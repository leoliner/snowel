## 一、产品定位

Snowel 是一款**本地单机**的 AI 小说创作辅助工具，面向超长篇小说（百万字级）的创作全流程。

- **核心命题**：雪花法是写作流程，不是数据模型——"从粗到细的生成路径"与"长篇创作中的知识管理"分开设计、再咬合。
- **运行形态**：作者在自己电脑上运行（本地 FastAPI + React 服务），不做多用户、不做云同步。事件溯源层为将来迁移预留路径，但当前版本不含相关需求。
- **项目单位**：一个项目 = 一个本地工作区目录，目录内含 Markdown 章节文件与一份 `snowel.db` 知识图谱。
- **三端一体**：Web（主创作界面）、MCP（供外部 AI 客户端）、CLI（本地管理），共享同一引擎核心。

### 1.1 目标用户与场景

| 用户 | 主要入口 | 场景 |
|---|---|---|
| 作者本人（产品主形态） | Web 三栏界面 | 从灵感到正文的全流程创作 |
| 习惯 AI 客户端的作者 | MCP（ZCode/Claude 等） | 用自然语言驱动全流程 |
| 脚本化/批量操作 | CLI | init、备份、导出、封卷等管理动作 |

### 1.2 非目标（当前版本明确不做）

- 多用户与云端协作
- 移动端
- 编辑器插件（Obsidian/VS Code 等）
- 内置发布/排版

## 二、总体架构

```
                    ┌─────────────┐
                    │  引擎核心    │  snowel-core（纯 Python，无 IO 框架依赖）
                    │  雪花流程    │  分形雪花 L1-5 / 卷级冻结线 / 章级小雪花
                    │  图谱+事件   │  本体 / 级联检查 / revision / 回写环 / 混合检索
                    └──┬───┬───┬──┘
                       │   │   │      三个外壳都是薄壳：参数校验 + 调用核心 + 回显
        ┌──────────────┘   │   └──────────────┐
   MCP Server (stdio)   CLI (typer)    FastAPI Backend ←→ React Web UI
   供任意 AI 客户端     本地管理/导出    作者主创作界面（全流程）
```

**架构铁律：**

1. **领域逻辑只存在于 `snowel-core`**：雪花流程、级联检查、提案-确认、回写、检索组装全部在核心内，可独立单测；三个外壳不得包含任何领域逻辑，出现绕过核心直调 LLM 的路径视为缺陷。
2. **LLM 调用只存在于三个口**：每层 `ai_generate`（提案生成）、`extract_and_writeback`（回写抽取）、检索改写（可选）。其余全部是确定性代码。
3. **提案-diff-确认范式贯穿三端**：AI 产出永远是提案，作者确认后才落库（确认分级见 5.3）。
4. **任何一端都不拥有独立状态**：提案、图谱、流程进度全部持久化在项目库中，三端视图一致。

## 三、数据与存储

### 3.1 双正典分层

| 正典 | 载体 | 内容 |
|---|---|---|
| 结构化正典 | `snowel.db`（SQLite） | 图谱节点/边、事件日志、提案、伏笔、时间轴、状态事件 |
| 叙事正典 | 工作区 Markdown 章节文件 | 章节正文，作者可用任意编辑器或 Snowel 内置编辑页修改 |

### 3.2 SQLite 单库（已定选型）

- 节点表 + 边表 + JSON 属性列；图遍历用递归 CTE。
- 全文检索：FTS5（中文分词 simple/jieba）。
- 向量：sqlite-vec，兜底语义召回。
- append-only 事件日志（见 5.4）。
- 明确不采用：Neo4j/外部图库、独立向量数据库。

### 3.3 正文与图谱的同步（回写 hook）

- 正文以 Markdown 文件为真相源；库中仅存正文索引与哈希用于变更检测。
- 文件监听 hook：检测到章节文件改动即触发 `extract_and_writeback` 更新图谱。
- 触发模式三种可配置：**自动（改动即触发）/ 手动（作者点击）/ 定时**。

### 3.4 提案的持久化

- AI 提案生成即入库（pending 状态），三端共享同一待确认队列，任一端确认/否决均生效。
- 事件日志只在提案**确认时**追加；pending 提案带过期/作废机制。

### 3.5 嵌入模型

- 默认本地中文模型（bge 系小模型，ONNX/sentence-transformers），离线可用零成本。
- 设置中可切换 API 嵌入（走 litellm）；切换触发全库向量重建与校验。

## 四、本体与知识图谱

（对应推演问题 #0 #1 #2 #3 #16 #17 #18 #20 #28 #30；正式 schema 定义是下游任务，此处为需求约束。）

1. **本体 = 小而通用的核心本体 + 可插拔属性组**。核心组（动机/谎言信念/恐惧/弧光等）永远在场；题材扩展包（无限流/玄幻/都市/恐怖…）只提供附加属性组，不做整模板替换；init 时不定题材，扩展包后挂，不影响已有数据。
2. **节点支持多类型叠加**（如制度型反派 = Concept + Character）。
3. **节点创建时机 ≠ 完备时机**：实体带 completeness 状态机（draft → profiled → active）。
4. **关系必须是节点**：Relationship 带起止拍与强度曲线；MicroBeat 挂 Scene 下，作为滚动上下文与伏笔微调粒度。
5. **多轨道 Timeline**：支持现实轨/异空间轨/回忆轨并行，场景挂轨+挂时长；Layer 4 展开前时间本体必须定稿。
6. **Mechanism 属性组**：规则原文/生效范围/漏洞/数值曲线（growth_curve 等护栏字段，指数增长在 Layer 1 警告）；narrative_role（advantage/finale/worldbuilding/red-herring）。
7. **灵感原话与提炼物分开存**：原始 brainstorm 全文永久保留为 Layer 1 附属，提炼物以 DERIVED_FROM 关联。
8. **伏笔为独立横切实体**：注册最早发生在 Layer 2；planted_at 支持多层定位（beat → scene → chapter 区间）且层间换算自动传播；AI 自埋伏笔必须标 `origin:"ai"`，作者有否决权；死亡角色 death_beat 锁定，检索自动附带"已死亡@拍N"。
9. **设定库是纵贯全流程的纵向轨道**：每层做「写入 + 缺口检查」两个动作；缺口可 TODO 化不强行填完；提供 `setting_gap_report`；fill_gap 落库后回显"图谱影响了什么"。

## 五、流程与一致性

### 5.1 分形雪花流程

```
🏔 大雪花（全书 L1-5）：灵感 → 梗概 → 摘要 → 节拍表 → 角色档案 → 场景卡 → 正文
 ❄️ 中雪花（卷/篇章）：输入本卷节拍区间 + 上卷末世界状态；卷级主题 → 卷级三幕 → 本卷场景卡滚动展开
 ✱ 小雪花（单章）：L1' 本章意图（一句话）→ L2' 微节拍（3-6 个）→ L5' 成文 → 与场景卡对账 → 回写环
```

- 300 章的书不在 Layer 4 一次排完，按卷滚动展开。
- 小雪花是受限展开不是从零生成：角色档案现成只需拉取；产出 MicroBeat 节点入图谱。
- 层级间允许修订（卷改书、章改卷），统一走同一套 revision 流程。

### 5.2 统一 revision 流程

「提案 → 级联影响分析 → 确认」——一次实现，三层（书/卷/章）复用。

### 5.3 确认分级（已定）

- **高敏感事实**（数字、人名、规则、角色生死等）：必须进确认队列，作者确认才入典。
- **低敏感事实**（描述性细节）：自动入典，但带 `auto` 标签，可在事后审阅视图中批量否决。
- 分级阈值可配置。
- 回写抽取提示词须带"忽略修辞"判据，防止把比喻当事实污染图谱。

### 5.4 事件溯源

- append-only 事件日志 + 物化当前图。
- 血缘（这个设定怎么来的，#5）、版本与旧版保留、回滚、retcon、级联检查的依据全部由事件溯源支撑。
- 正文文件哈希变更也记录为事件。

### 5.5 级联检查（双向，#9）

- 写入新数据时向前查矛盾；修改旧数据时向后查依赖（含 IS_A/REQUIRES/EXPLOITS 边反查）。
- 冲突时生成 diff 式修订提案，不自动改。

### 5.6 冻结线与 retcon（已定）

- **封卷 = 显式命令**（CLI `snowel seal` 或 Web 按钮），作者主动决定何时冻结。
- 未封卷时写后续卷只给警告不阻断。
- 已封卷的设定改动必须走显式 retcon 流程（级联影响分析 + 确认）。

## 六、检索与上下文组装

（对应 #23 #25 #26 #27；Layer 5 的生死线。）

1. **写前 `compose_context`**：图谱精确拉取为主（场景卡 + 在场角色档案按需裁剪 + 未回收伏笔 ∩ 相关项 + 已确认世界观，TODO 项排除），FTS5/向量兜底召回相似正文；300 章后必须精确到"当时在场角色 + 当时未回收伏笔"。
2. **检索审计 `retrieval_audit`**：记录每次上下文组装了什么；作者事后标记"AI 忘了 X"，用真实失误数据校准检索策略。
3. **回写抽取成本控制**：每章多一次 LLM 调用；低重要章节可批量抽取或用小模型。
4. LLM 接入统一走 **litellm**：生成用大模型、抽取可用小模型，供应商可换。

## 七、三端交互

### 7.1 Web 创作界面（产品主形态，已定布局）

- **三栏布局**：左侧流程树（Layer 1→5 → 卷 → 章，实时反映项目状态与待办）；右侧工作区（各层表单/卡片/diff 确认面板）；中间正文编辑页（绑定本地工作区，识别其中的 Markdown 章节文档）。
- 常驻聊天侧栏：自然语言对话，可代填表单、发起提案，但**确认动作永远落在结构化面板**上。
- Web 后端 FastAPI 只做路由/会话，穿过 core 调用 litellm；图谱通过 compose_context（进）与 extract_and_writeback（出）参与每次对话，不绕过 core。
- 另提供只读可视化：POV 分布、伏笔地图、角色关系、节奏统计（纯统计非 AI）。

### 7.2 MCP Server（已定粒度）

**平铺 5 个高频工具 + 1 个入口工具，合计 6 个：**

| 工具 | 职责 |
|---|---|
| `snowel_status` | 项目状态：流程走到哪层、待确认提案、未回收伏笔、设定缺口 |
| `snowel_generate` | 创作主力：参数指定产物类型（premise/summary/beat_sheet/scene/正文…），内部路由到对应层 ai_generate |
| `snowel_query` | 图谱查询：角色档案、关系、时间轴、伏笔状态、全文/语义检索 |
| `snowel_proposal` | 提案队列操作：列出/查看 diff/确认/否决/改写 |
| `snowel_writeback` | 回写环：手动触发抽取、查抽取结果、否决 auto 入典条目 |
| `snowel_advanced` | 长尾入口：无参调用返回操作目录（设定缺口管理、机制具体化、伏笔注册、封卷/retcon、题材包、审计、可视化统计） |

- 传输：stdio 起步，streamable HTTP 后续。
- 设计约束：列表永不膨胀——新能力一律进 `snowel_advanced`，不动平铺层。

### 7.3 CLI

- `typer` 薄壳，只做本地管理：`init` / `status` / `export`（Markdown/txt）/ `seal` / `backup` 等。
- 不做交互式创作。

## 八、技术选型汇总（已定稿）

| 层 | 选型 |
|---|---|
| 语言 | Python 3.12+ |
| 引擎核心 | 纯 Python 包 `snowel-core` |
| MCP | 官方 `mcp` Python SDK（stdio 起步） |
| CLI | `typer` |
| Web 后端 | `FastAPI` |
| Web 前端 | `React` + Vite + TypeScript |
| 存储 | SQLite 单库（节点/边表 + JSON + 递归 CTE） |
| 全文 | FTS5 + simple/jieba 分词 |
| 向量 | sqlite-vec；嵌入默认本地 bge 系，可切 API |
| LLM | litellm |
| 校验/统计 | 纯 Python |

## 九、落地顺序

1. **snowel-core**：本体 schema + 事件溯源存储层 + 基础图查询（支撑 Layer 1/2）
2. **MCP + CLI 薄壳**：接入 AI 客户端验证流程
3. **回写环 + 混合检索**：含文件监听 hook、检索审计（Layer 5 生死线）
4. **Web 三栏创作界面**：产品形态收口

> 顺序理由：Web 是最终形态但不是第一验证工具；先在 MCP/CLI 里低成本跑通流程与图谱，核心稳定后再包 Web 壳。
